# SPIKE #100 — index FK-scalar (relation) fields for probe-not-scan traversal

> **Status: LANDED 2026-07-10.** Both required (`*Target`) and optional (`?Target`, riding #102) FK
> fields are indexed; reverse one-to-many getters now probe `find_by_<fk>` instead of scanning. Guard
> `test_rust_generation_index_followups`; E2E `scratchpad/followups_compile`. M2M junction-column
> indexing remains the deferred second step.

Design spike for issue #100, a Phase 2 (#90) follow-up. Builds directly on the secondary-index
machinery landed in #90 (`crates/codegen/src/rust.rs`). Verified against the generated code as
of 2026-07-10.

## TL;DR recommendation

**Reuse the #90 index verbatim for FK-scalar columns, then rewrite the generated reverse-relation
getters to probe it.** Add `RequiredReference` (→ `Uuid`) FK fields to `indexed_fields`, key them
with the existing `index_key_expr`, and change `generate_traversal_impl`'s reverse one-to-many /
M2M getters from an `all()` scan filtering on the FK to a `child.find_by_<fk>(parent_id)` probe.
This is **~90% wiring of existing #90 code** — the only genuinely new work is the getter rewrite.
Defer **optional FK** (`?Model` → `Option<Uuid>`) to ride #102 (nullable indexing); do required
FK first.

## The deciding insight

#90 already eliminated the scan for scalar lookups. The *reverse-relation* getters
(`user_posts(id)`, `post_tags`, eager-load) are the **last linear `all()` scans in the read
path**, and they scan on exactly one thing: a **foreign-key Uuid column**. An FK column is a
scalar `Uuid` (`RequiredReference` maps to `Uuid` in `map_field_type_ident`, stored as a 16-byte
fixed column) — structurally identical to any `^`/`&` `uuid` field #90 already indexes. The only
reason it isn't indexed today is a deliberate one-line exclusion: `is_filterable_scalar` (and its
`ApiGenerator` twin `is_filterable_field`) return `false` for `FieldType::Relation(_)`.

So the index structure, maintenance, reopen-rebuild, and snapshot-`_at` resolution are **already
built and proven**. FK indexing is: (1) let FK fields into `indexed_fields`, (2) probe from the
reverse getter.

## Design

### 1. Admit FK-scalar fields to the index

`indexed_fields(model)` currently requires `is_filterable_scalar(field_type)`, which excludes
relations. FK fields have no `^`/`&` modifier (the relation *is* the index intent), so the
selection predicate changes from "has `^`/`&` modifier" to **"has `^`/`&` modifier OR is a
`RequiredReference`"**:

```rust
fn indexed_fields(model) -> Vec<&Field> {
    // ... existing id-guard ...
    model.fields.iter().filter(|f| {
        let is_fk = matches!(f.field_type,
            FieldType::Relation(RelationType::RequiredReference(_)));
        ((f.indexed || f.unique) && is_filterable_scalar(&f.field_type) && !nullable)
            || is_fk                         // FK cols: always indexed, key type Uuid
    }).collect()
}
```

`index_field_ident` (`<field>_index`), the `HashMap<String, HashSet<Uuid>>` field, `index_add_block`
/ `index_remove_block`, and `index_key_expr` all work unchanged: the FK struct field is a `Uuid`,
and `serde_json::to_value(&uuid)` → `Value::String(hyphenated)` → the canonical key, exactly like
an indexed `uuid` scalar. Maintenance sites (insert/update/delete) and the reopen rebuild in
`generate_rehydrate_logic` pick it up **for free** because they all iterate `indexed_fields`.

### 2. Rewrite the reverse getters to probe

`generate_traversal_impl` today emits reverse one-to-many getters as a scan:

```rust
pub fn user_posts(&self, user_id: Uuid) -> Vec<Post> {
    self.post.all().into_iter().filter(|p| p.author == user_id).collect()   // O(rows)
}
```

Rewrite to a probe against the child's FK index:

```rust
pub fn user_posts(&self, user_id: Uuid) -> Vec<Post> {
    self.post.find_by_author(user_id)                                        // O(1) + resolve
}
```

The `find_by_<fk>` probe is generated by #90's `generate_index_lookups` the moment the FK field
enters `indexed_fields`. The multi-FK disambiguation getters (`user_posts_by_author`) map to
`find_by_<specific_fk>` the same way. M2M getters (`post_tags`) resolve through the junction and
are a separate scan — leave them to the junction-index question, out of this spike's core (note
below).

### 3. Snapshot-scoped reverse traversal

`generate_traversal_impl` has no `_at` reverse getters today, but #90 generated `find_by_<fk>_at`
for the FK the moment it is indexed. If/when snapshot-scoped reverse traversal is wanted, it is
`self.post.find_by_author_at(snap, user_id)` — no new machinery.

## Constraints (inherited, all already satisfied by #90)

- **Commit boundary / superseding-version (#89/#66):** maintenance runs at the same insert/update/
  delete sites, after the WAL commit; an FK that changes on `update` correctly drops the old
  parent bucket and adds the new one. ✅ (falls out of using `indexed_fields`).
- **Snapshot isolation (#56):** `_at` probes resolve through `get_at` + post-filter. ✅
- **Reopen:** FK index rebuilt in the same id-scan. ✅
- **Identity:** generated, schema-tailored index + probe — no runtime engine. ✅

## Tradeoffs / decisions

- **Required vs optional FK.** `RequiredReference` → `Uuid` is a clean scalar; do it here.
  `OptionalReference` → `Option<Uuid>` needs the `None`-bucket + `Option` param handling that
  **#102** designs — sequence #100 to land required FK, then optional FK rides #102's nullable
  work. State this in both issues.
- **Every FK gets an index, unconditionally.** Unlike `^`/`&` (opt-in), FK indexing is
  not user-signalled. That's correct: a reverse getter is *always* generated for a one-to-many,
  so the scan it replaces always exists. Memory cost is one `HashMap` entry per child row — the
  same order as `id_to_row`.
- **M2M junctions.** `post_tags` scans the junction's `pairs()`. Indexing the junction's two Uuid
  columns is analogous but touches the junction structs (`generate_junction_structs`), not model
  storage — fold into this issue as a second step, or split. Recommend: **required-FK first
  (highest value, lowest risk), junction index as a follow-up step on the same issue.**

## Recommended plan

1. Extend `indexed_fields` to admit `RequiredReference` FK fields (key type `Uuid`).
2. Confirm `generate_index_lookups` emits `find_by_<fk>` for them (no `&unique` → Vec probe only,
   which is exactly what reverse one-to-many wants).
3. Rewrite reverse one-to-many getters in `generate_traversal_impl` to call `find_by_<fk>`.
4. Guard: extend `test_rust_generation_relation_traversal` to assert the reverse getter body is a
   `find_by_` probe, not `.all().into_iter().filter`.
5. E2E: insert parent + N children, assert `user_posts` returns them via probe; snapshot variant.
6. (Optional second step) index junction columns + rewrite M2M getters.

**Scope:** 1 codegen file (`rust.rs`), 1–2 guard tests, 1 scratchpad E2E. No new substrate, no
publish gap (query-params already published; this is pure generated code over existing storage).
