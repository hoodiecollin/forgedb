ForgeDB generates in-memory secondary indexes and typed probe methods so reads never scan
the whole table. Each indexed field gets a `value → {id}` map maintained in lockstep with
your writes and rebuilt on reopen. Probes are an O(1) index lookup that resolves candidates
through the version-aware read path — not a scan.

All of this is generated per model. The index maps live in generated code over the existing
storage; no runtime engine reads your schema.

## Declaring indexes

Mark a field with the `^` index modifier (or `&` for a unique index) in your schema:

```forge
User {
  id: +uuid
  email: &string      // unique index
  status: ^string     // secondary index
  created_at: ^timestamp
}
```

## Single-scalar probes

Each indexed scalar field gets `find_by_<field>` (returns all matches) and `get_by_<field>`
(returns the first), plus `_at` variants for snapshot reads:

```rust
let admins = db.user.find_by_status("admin");   // O(1) index lookup, not a scan
let user = db.user.get_by_email("a@b.com");      // Option<User>

// Point-in-time variants resolve the snapshot's version:
let snap = db.user.snapshot();
let past = db.user.find_by_status_at(&snap, "admin");
```

The index is maintained around the durable write boundary: added on insert, remove-old +
add-new on update (superseding-version aware), dropped on delete. On reopen it is rebuilt
folded into the same id-scan that rebuilds `id_to_row`, reading only the indexed columns.

## Foreign-key indexes

Foreign-key scalar fields (`*Target` required, `?Target` optional) are **always** indexed —
a reverse one-to-many getter that would otherwise scan always exists. The generated reverse
getters probe the FK index instead of scanning:

```rust
let posts = db.user_posts(user_id);   // O(matches) FK-index probe, not O(rows)
```

When a child has multiple FKs back to one parent, the getter disambiguates by child field
(e.g. `user_posts_by_author`).

## Composite indexes

Declare a model-level `@index(a, b)` to index a combination of fields:

```forge
Event {
  id: +uuid
  tenant: ^uuid
  status: string

  @index(tenant, status)
}
```

This generates `find_by_<a>_and_<b>` (and `_at`) keyed by a collision-free length-prefixed
concatenation of the component keys, so `("ab","c")` and `("a","bc")` never collide.

<Callout type="warning" title="Composite hash indexes answer exact-match only">
A composite index answers `a = ? AND b = ?`. It does **not** answer a prefix or a range over
its components — that is a B-tree feature and out of scope for the hash index.
</Callout>

## Nullable indexes

Nullable scalar fields are indexable. Probe parameters are `Option<T>` (`Option<&str>` for
strings), so `find_by_<field>(None)` probes the unset bucket:

```rust
let unassigned = db.ticket.find_by_assignee(None);
```

The index key is null-distinct and type-tagged, so `None` and the literal string `"null"`
cannot collide.

## Ordered / range indexes

Hash indexes are exact-match only. For **ordered range and top-N** queries, an
ordered-eligible non-nullable indexed field also gets a parallel ordered (B-tree) index keyed
by the typed value. Eligible types are the `Ord` keys: `u32`, `u64`, `i32`, `i64`,
`timestamp`, and `decimal`.

```forge
Post {
  id: +uuid
  views: ^u64          // ordered-eligible → gets a range index
}
```

This generates `find_by_<field>_range`:

```rust
// WHERE views >= 100 ORDER BY views DESC LIMIT 10
let top = db.post.find_by_views_range(Some(100), None, /* descending */ true, /* limit */ Some(10));
```

The range walk is O(offset + limit) in value order. The ordered index is **parallel** to the
exact-match hash index, not a replacement — the hash index still serves `&unique`, FK, and
reverse-FK lookups. Eligibility is automatic by field type; there is no directive to choose
between hash and ordered.

<Callout type="note" title="Ordered-index exclusions">
`f64` is excluded (no clean total order). **Nullable** ordered indexes are deferred. Decimal
keys are normalized (scale-invariant), so `1.0` and `1.00` share a bucket.
</Callout>

## Limits

- **Hash indexes are exact-match only** — no prefix or range on the hash path; use an ordered
  index (above) for ranges over eligible types.
- A read-only reader handle shares the index maps by reference; the writer mutates a
  copy-on-write copy.
- `json` fields are never indexable, filterable, or sortable (JSON has no total order).

Indexes also power the REST list endpoint's filter pushdown — see
[Live queries & change feed](/docs/features/live-queries/) for the shared closed-set matcher
and [Point-in-time reads](/docs/features/snapshot-reads/) for the `_at` snapshot probes.
